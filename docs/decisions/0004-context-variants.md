# 0004 将上下文窗口变体展开为独立模型条目

Status: accepted
Date: 2026-11-25

## 背景

Cursor 模型目录通过 `context` 参数描述同一模型的不同上下文窗口档位（如 `300k`、`1m`），不同档位对应各自的变体参数，部分长上下文档位还要求开启 `Max Mode`。而 DSH 的模型选择器采用扁平的「提供方 + 模型 ID」结构，没有独立的上下文档位二级菜单；同时，DSH 的自动上下文压缩依赖 `resolveModel` 返回准确的上下文容量。

如果每个模型只向 DSH 注册一个条目：

- 用户无法在界面上按需切换标准上下文与长上下文档位。
- DSH 只能按固定值估算压缩阈值——估大了会导致请求超限报错，估小了又会过早触发压缩丢失细节。
- 调用非默认档位时，SDK 需要完整的变体参数与 `maxMode` 标记，仅传基础模型 ID 无法生效。

## 决策

由 `toModelInfos()` 将模型的每个 `context` 可选档位拆分为独立的 DSH 模型条目：

- 目录默认档位保持原始 Cursor 模型 ID，兼容已有会话保存的选择。
- 其余档位使用 `<model>::context=<encodeURIComponent(value)>` 作为 DSH 内部模型 ID，由 `modelRouteOf()` 在请求时拆回真实模型 ID 与 `context` 值。
- 所有展开条目的展示名称统一加上 ` · <档位显示名>` 后缀（含默认档位），方便用户在列表中直观区分。
- `resolveModel()` 按所选档位返回解析后的真实 Token 容量；仅当模型目录不含 `context` 参数（或档位文本无法解析）时，才回退使用配置的 `contextWindow`（默认 `128000`）。
- `modelSelection()` 优先选用同时匹配 `context` 与 `reasoningEffort` 的目录完整变体；若无精确匹配组合，则基于该 `context` 的基础变体合并参数，且仅在该 `context` 下所有变体均要求 `Max Mode` 时自动附加 `maxMode: true`。

## 影响

- 支持多档位上下文的模型会在选择器中展示为多行；普通模型 ID 始终有效，拼接 ID 的解析规则需保持向后兼容。
- 若上游后续下线某个历史上下文档位，旧选择会明确报 `UNSUPPORTED_CONTEXT`，提示用户重新选择模型。
- 长上下文与 `Max Mode` 可能产生更高计费消耗，需在展示名称和说明文档中予以提示。
- `contextWindow` 配置项仅承担无目录信息时的兜底角色，不会覆盖目录已披露的真实容量。

## 备选方案

- **每个模型只暴露单一固定条目**：列表更简短，但用户无法切换上下文档位，自动压缩阈值也无法对齐真实窗口，放弃。
- **在插件配置中提供全局上下文容量开关**：无法按不同模型分别设置，且容易与模型实际支持的档位冲突，放弃。
- **默认一律选用最大上下文档位**：可能在用户不知情时触发长上下文高额计费，放弃。
- **借用 `reasoningEffort` 下拉框承载上下文档位**：混淆了「上下文容量」与「推理思考强度」两个独立维度，且无法与真实推理强度共存，放弃。
